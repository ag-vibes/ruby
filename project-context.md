# Ruby — контекст продукта и спецификация для разработки

## Правило согласованности изменений

Перед каждой новой правкой сверять её с уже принятыми продуктовыми решениями, моделью данных и связанными сценариями. Если новое изменение создаёт конфликт или нелогичность, сначала устранить несостыковку и только затем реализовывать правку.

Любое удаление уже сохранённых результатов, курсов или показателей требует подтверждения внутри интерфейса Ruby. Удаление несохранённой строки из динамической формы подтверждения не требует.

Горизонтальная прокрутка графиков должна сохранять инерцию жеста на iPhone в Safari; все графики при этом продолжают прокручиваться синхронно.

Название `ruby` в интерфейсе отображается синим цветом Ruby. Иконка приложения на текущем этапе — однотонный голубой фон `#B7D1F3` без маскота и красных элементов.

## 1. Что это за проект

**Ruby** — личное мобильное веб-приложение для отслеживания динамики лабораторных показателей здоровья во времени.

Главная задача приложения — не архивировать анализы ради прошлого, а помогать поддерживать здоровье в будущем: видеть, как меняются важные показатели, как они реагируют на курсы препаратов/добавок и как со временем снижаются после окончания курса.

Основной сценарий — несколько раз в год вносить новые результаты анализов и периодически отмечать курсы, которые влияют на конкретный показатель.

Приложение рассчитано прежде всего на использование с телефона. Синхронизация между устройствами не нужна.

## 3. Название и смысл

Название приложения: **ruby**.

Почему:

- ruby — физический объект, который можно превратить в маскота;
- рубин ассоциируется с кровью, жизненной силой и ценностью;
- большая часть лабораторных показателей определяется из крови;
- первоначальный и важный сценарий связан с железом / ферритином / гемоглобином;
- при этом название не настолько буквально медицинское, как капля крови или пробирка;
- смысл приложения шире железа: это забота о здоровье и поддержание собственного ресурса.

Название в интерфейсе писать строчными: `ruby`.

## 5. Маскот Ruby

Ruby должен быть выполнен в той же общей иллюстративной логике, что и маскот Cushion:

- плоский 2D;
- простой;
- дружелюбное лицо;
- тёмные глаза и улыбка;
- мягкая обводка;
- без реалистичного 3D;
- без сильных бликов;
- без сложной текстуры.

### Утверждённая форма

Использовать **широкий камень**, а не каплю:

- верх — выраженно острый;
- низ — плоский;
- корпус достаточно широкий;
- должно сразу читаться, что это огранённый камень/рубин;
- не вытягивать маскота вертикально.

### Грани

Грани нужны, чтобы объект читался как камень, но:

- линий должно быть мало;
- они должны быть тонкими;
- они должны быть заметно светлее/мягче основной обводки;
- нельзя создавать ощущение трещин на лице;
- центральная область лица должна оставаться чистой.

### Важное замечание

Сгенерированный ранее файл `ruby-favicon.svg` **не является утверждённым визуальным ассетом**: форма маскота в нём не совпала с выбранным визуальным референсом.

При разработке финальные favicon / app icons нужно подготовить заново на основе утверждённого широкого Ruby из визуального макета.

На самом первом рабочем этапе приложения маскот можно вообще не использовать внутри интерфейса. Сначала важна работающая продуктовая логика. Маскот и дополнительные иллюстрации можно довести позже.

# 7. Справочник показателей

Справочник создаётся и настраивается отдельно.

Для каждого показателя хранить:

- `id`
- название;
- единицу измерения;
- порядок;
- показывать ли на главной.

Пример:

- ферритин — мкг/л
- гемоглобин — г/л
- железо — мкмоль/л
- витамин D — нг/мл

### Начальный справочник

При первом запуске создать показатели в таком порядке:

- гемоглобин — г/л
- ферритин — мкг/л
- железо — мкмоль/л
- витамин D — нг/мл
- фолиевая кислота — нг/мл

Трансферрин в начальный справочник не добавлять.

### Почему единицы хранятся в справочнике

При регулярном вводе пользователь **не вводит единицы измерения**.

Пользователь работает с показателем как:

> ферритин — 24

Единица уже известна системе.

Если появился новый показатель, например трансферрин, пользователь один раз создаёт его в справочнике и задаёт единицу. После этого в обычной форме результатов вводит только число.

### Порядок

Показатели можно вручную переставлять **drag-and-drop**.

Этот порядок используется:

- на главной;
- в выпадающих списках;
- в справочнике.

Не делать:
- «часто используемые»;
- авторанжирование;
- «показывать по умолчанию»;
- категории показателей.

Пользователь сам один раз задаёт удобный порядок.

Список плоский, без групп «железо / витамины / щитовидка» и т. п.

# 8. Добавление результатов

Основная кнопка:

**`добавить результаты`**

Она расположена на главной сверху над графиками.

### Форма

При открытии:

1. поле **дата**;
2. одна строка результата:
   - **показатель** — select из существующего справочника;
   - **значение** — числовое поле;
3. кнопка **`добавить ещё показатель`**;
4. кнопка сохранения.

По умолчанию показывается только одна строка результата.

По нажатию `добавить ещё показатель` появляется ещё одна пара:

- показатель;
- значение.

Можно за одну дату внести:
- один показатель;
- два;
- три;
- сколько нужно.

### Важное ограничение

Из формы `добавить результаты` **нельзя создавать новый показатель**.

Новые показатели добавляются только через справочник на экране `ещё`.

### Числа

Пользователь вводит десятичные значения **через запятую**:

- `39,4`
- `8,6`
- `1,14`

На экране тоже показывать через запятую.

Не заставлять пользователя вводить точку.

# 9. Главная

Главная — это **дашборд графиков**, а не список анализов.

Вверху:

- название / header;
- `добавить результаты`;
- `отметить курс`.

После этого — графики показателей.

Каждый показатель отображается отдельным блоком.

Порядок блоков совпадает с порядком в справочнике.

Показатели, у которых выключено «показывать на главной», здесь отсутствуют.

# 10. Графики

Это ключевой элемент приложения.

## Общий принцип

Один показатель = один отдельный график.

Не объединять на одной шкале:

- ферритин;
- витамин D;
- гемоглобин;
- другие показатели.

### Временная шкала

Ось X — реальное календарное время.

**На ширину экрана помещается 12 месяцев.**

Если история длиннее, график можно двигать горизонтально свайпом.

Расстояния между точками зависят от реальных дат.

Пример:

- октябрь → февраль занимает примерно треть годовой ширины;
- две точки не должны растягиваться на весь экран только потому, что других измерений нет.

### Ось Y

**Вертикальной Y-оси нет вообще.**

Не показывать:

- числа слева;
- grid lines;
- горизонтальные разделители;
- 0 / 25 / 50;
- референсные диапазоны.

График должен оставаться визуально чистым.

### Точки

Каждая точка подписана своим реальным значением.

Формат:

```text
  39,4
    ●
```

Число:
- расположено прямо над точкой;
- центрировано относительно точки.

Пользователь читает конкретные значения именно по этим подписям.

Не делать tap/tooltip обязательным для просмотра значения.

### Ось X

На X отображаются месяцы.

Она остаётся единственной видимой осью графика.

Сейчас основная задача — личная динамика.

# 12. Курсы

Вторая основная кнопка на главной:

**`отметить курс`**

Курс связан с **одним или несколькими показателями**.

Например:

- курс железа может быть одновременно привязан к графикам железа, ферритина и гемоглобина;
- курс витамина D — к витамину D.

Связи выбирает пользователь вручную; приложение не определяет физиологические связи автоматически.

## Данные курса

Хранить:

- `id`
- `indicatorIds`
- `startDate`
- плановую дату окончания — если была;
- фактическую дату окончания — если курс завершён;
- количество дней — если было указано.

### Форма курса

Обязательно:

- показатель;
- дата начала.

Необязательно:

- дата окончания;
- количество дней.

Если поле необязательное — использовать тот же UI-паттерн, что в Cushion: подпись **`(не обязательно)`**.

### Количество дней

Пользователь иногда знает не дату окончания, а длительность/количество дней.

Можно ввести:

> 90 дней

Приложение рассчитывает предполагаемую дату окончания.

Не добавлять:
- количество таблеток в сутки;
- название препарата;
- дозировку.

По пользовательскому сценарию длительность важнее конкретного препарата.

### Плановая и фактическая дата

В интерфейсе не нужно заставлять пользователя думать о двух разных полях одновременно.

Но технически стоит различать:

- `plannedEndDate`
- `actualEndDate`

Например:
- при создании курса рассчитано окончание 1 марта;
- реально курс завершён 10 марта.

После завершения сохраняется фактическая дата.

Если дата окончания при создании неизвестна, курс остаётся активным.

# 13. Отображение курса на графике

Курс находится внутри того же графика показателя.

Пользователь обычно сдаёт анализ:

- до начала курса;
- затем принимает курс;
- повторно сдаёт после окончания.

Поэтому внутри самого периода курса точек часто вообще не будет.

### Визуальная идея

- вертикальная штриховая линия в дату начала;
- вертикальная штриховая линия в дату окончания;
- между ними горизонтальная штриховая линия;
- на ней подпись **`курс`**.

Не подписывать отдельно «начало» и «конец»: направление времени и границы и так понятны.

Горизонтальная линия курса не должна кодировать значение по Y.

Её высота — служебная и постоянная внутри карточки графика.

Если курс ещё идёт:
- есть граница начала;
- линия продолжается вправо;
- фактической границы окончания пока нет.

Финальный визуальный вариант можно уточнять на прототипе, но смысл именно такой.

# 14. Экран «ещё»

Нижняя навигация состоит всего из **двух пунктов**:

- `главная`
- `ещё`

Использовать постоянную нижнюю navigation bar по принципам Cushion.

Экран `ещё` содержит три блока.

## Показатели

Справочник:

- название;
- единица;
- drag-and-drop;
- добавление;
- редактирование.

## История

История сгруппирована **по показателям**, а не по датам.

Пример:

```text
ферритин

01.03.2026        39,4        ✎
15.01.2025        48          ✎
20.08.2024        17          ✎
```

Для редактирования — **иконка карандаша**, не слово «изменить».

Здесь можно:
- исправить результат;
- удалить ошибочную запись.

Существующие активные и завершённые курсы также находятся в истории
соответствующего показателя. Здесь их можно редактировать и завершать.

### Не показывать на главной

Под историей показателя есть toggle/checkbox:

**`не показывать на главной`**

Если включено:
- показатель остаётся в истории;
- данные не удаляются;
- показатель исчезает с главной.

Отдельную сущность «архив» пользователю не показывать.

## Резервная копия

Перенести механику резервной копии из Cushion:

- экспорт;
- импорт / восстановление.

Основные данные всё равно живут в IndexedDB на одном устройстве.

Backup — страховочная функция, а не часть ежедневного сценария.

- отдельный drill-down по тапу на график;
- tooltips для чтения значения;
- сложную систему цветов.

---

# 16. Почему не показываем изменение к предыдущему значению

Сравнение с предыдущей точкой само по себе вводит в заблуждение.

Например:

- после курса ферритин закономерно вырос;
- через несколько месяцев без курса он закономерно снизжается.

`−12` или `+20%` ничего полезного без контекста курса не сообщает.

Поэтому главная показывает:
- траекторию;
- конкретные числа;
- курсы;
- время.

Но не формирует искусственную оценку «стало лучше / хуже» по соседним измерениям.

---

# 17. Начальные исторические данные

Не требуется переносить всю медицинскую историю.

Первоначальный план — внести в основном:
- прошлый год;
- текущий год.

Но архитектура должна поддерживать более длинную историю.

Графики с историей больше года доступны горизонтальным скроллом.

---

# 18. Визуальный характер

Ruby должен быть:

- спокойным;
- дружелюбным;
- не клиническим;
- не похожим на медицинскую CRM;
- не «wellness-ванильным»;
- не чрезмерно эмоциональным;
- mobile-first;
- достаточно простым, чтобы внесение анализов несколько раз в год не требовало вспоминать сложную механику.

Главное правило UX:

**поскольку приложение используется редко, оно должно быть самоочевидным, а не оптимизированным под power-user workflow.**

---

# 19. Порядок разработки

Рекомендуемый порядок:

1. изучить актуальный `ag-vibes/cushion`;
2. переиспользовать его базовую архитектуру и UI-принципы;
3. создать структуру данных Ruby;
4. реализовать справочник;
5. реализовать ввод результатов;
6. реализовать графики;
7. реализовать курсы и их отображение;
8. реализовать историю;
9. перенести backup;
10. проверить mobile layout на iPhone;
11. только после рабочей версии доводить маскота и иконки.

Не начинать разработку с маскота.

# 20. Контрольный UX-сценарий

## Внести анализ

Пользователь открывает Ruby → `добавить результаты` → выбирает дату → выбирает `ферритин` → вводит `24` → при необходимости нажимает `добавить ещё показатель` → добавляет `гемоглобин 138` → сохраняет.

Графики обновляются автоматически.

## Начать курс

Пользователь → `отметить курс` → выбирает показатель `ферритин` → вводит дату начала → при желании вводит 90 дней → Ruby рассчитывает предполагаемое окончание → сохранить.

На графике ферритина появляется отметка курса.

## Завершить курс

Пользователь открывает существующий активный курс → указывает фактическую дату окончания → сохранить.

График обновляет границу курса.

## Исправить старый результат

`ещё` → `история` → `ферритин` → карандаш напротив нужной даты → исправить → сохранить.

# 21. Открытые визуальные вопросы, которые можно решать уже на прототипе

Продуктовую механику не нужно снова пересобирать. Открыты только детали визуальной реализации:

- точная высота служебной линии курса внутри графика;
- размер и отступ подписей значений;
- формат подписей месяцев на X;
- поведение горизонтального скролла между 12-месячными периодами;
- окончательная версия Ruby mascot asset.

Все эти решения нужно проверять на реальном mobile-прототипе, а не добавлять новые продуктовые сущности.
